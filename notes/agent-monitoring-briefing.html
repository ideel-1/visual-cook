Two Agents, One Design System

You ship a design system as a zip. His Claude Code applies it to the machine console. How do you see what his agent does, and how do the two agents stop talking past each other?

Short answer

  • Watching him live under your own login is not a thing in Claude Code. Open feature request. What you can do: he shares a read-only session link (zero setup), his session transcripts get committed into git so you read them with a CLI (Entire, 10 minutes), or every tool call from both your laptops streams to one dashboard on the office Wi-Fi (an evening).
  • Yes, companies have built multiplayer agent views. Amp, Warp, Cursor, Devin, Codex and Anthropic's own cloud sessions all let teammates open each other's runs. Details in the table below. For two people on Claude Code with a self-hosted GitLab, none of them is worth switching for. The one idea worth stealing, shared threads, you get from Entire without leaving the terminal.
  • Your agents cannot message each other. Cross-session messaging works across machines only inside one account. Between two people the mailbox is a GitLab issue with a fixed template.
  • The zip is the actual problem. Tokens as JSON, rules in a file the agent loads by itself, and a check it can run. That removes more misunderstanding than any monitor.
  • Adoption: put everything in the repo and in the admin console. Nobody installs anything for the pilot. Rules, skill, hooks and issue template are files in the console repo, so they apply to whoever opens it, in Claude Code, Cursor, Codex or Gemini. Company-wide, one admin pushes the Claude Code parts from claude.ai. Details in "Rollout".

Where each signal goes

His agent runs on his laptop. Everything you can see is a copy that laptop sends somewhere. Three destinations, three kinds of view.

Seven ways to watch

Rated on: live or not, works on a phone, setup cost, who else can use it. Options 01 and 02 need no infrastructure. 03 and 04 are the "see each other's agents" answers. 05 and 06 make GitLab and chat the shared surface. 07 is the screen-share idea done properly.

01

He mirrors his session and shares the link

Remote Control mirrors a local Claude Code session to claude.ai/code and the Claude phone app, with a diff pane of his uncommitted changes. Sessions there have a visibility toggle. Team and Enterprise plans get Private or Team. Pro and Max get Private or Public. You see the latest state when you open the link. It does not update live.

  • LiveOn refresh
  • PhoneYes
  • SetupOne command
  • Who seesYour org, or anyone

You get the whole conversation: his prompts, the agent's reasoning, tool calls, diff. Richest single view of "what is it stuck on". It lives in his account, so he owns the toggle and you only read.

Limits. Needs a claude.ai login on his side, not an API key, Bedrock or a company LLM gateway. On Team plans an Owner must switch Remote Control on in admin settings. The share toggle is documented for cloud sessions. Remote Control sessions sit in the same list, but test that the toggle shows for his session before relying on it. Real multi-user viewing is an open request (Claude Code issues 40981 and 60082).
Commands
  1. In his project: claude --remote-control "console restyle", or /remote-control in a running session.
  2. Open the session at claude.ai/code, set visibility to Team, send the link.
  3. End of run: /export restyle-1.md dumps the conversation to a file.

Also useful: claude -p --resume <session-id> "list every place the design system was unclear" asks a finished transcript a question. Runs only on the machine that holds the transcript.

02Best fit for two terminals + GitLab

His session transcripts get committed to git. You read them with a CLI.

Entire is an open-source CLI (MIT, 5k stars) from GitHub's former CEO. Once enabled in a repo, it hooks Claude Code and, at every commit, stores the full session next to the commit as a checkpoint: transcript, prompts, tool calls, files touched, token use. Checkpoints live in git refs under refs/entire/, so they push and pull like anything else and never show up in the branch history. Works with any git host, GitLab included. No account needed to read them.

  • LivePer commit
  • PhoneTerminal
  • Setup10 minutes each
  • Who seesAnyone who can pull

You pull his branch, run entire checkpoint explain <id> or entire search "Button", and read what his agent did and why for that commit. Your own Claude Code session can read the same checkpoints, which is the closest thing to your agent understanding his agent. This is the shared-thread idea from Amp and Warp, but inside git and without changing tools.

Limits. After the fact, not live. Granularity is a commit, so ask him to commit often during a restyle. Transcripts go into the repo; decide whether the console repo is the right home or whether a fork of the design-system repo is. CLI only, no web viewer, so not a phone thing.
Setup 
brew tap entireio/tap && brew install --cask entire
cd console-app && entire enable       # he does this once
# ... he works with claude as usual, commits, pushes ...
git pull && entire checkpoint list    # you, on your laptop
entire checkpoint explain 3f2a9c1
03Best live view of everyone's agents

Every tool call posts to a dashboard on the LAN

Claude Code fires a hook at about thirty moments per session: before and after every tool call, on failure, on permission requests, on stop. A hook can be an HTTP POST of the event JSON to any URL. Point it at a small server on a spare office machine and you have a live timeline of every agent in the room, per person, per session. Two open-source dashboards already do this.

  • LiveUnder a second
  • PhoneBrowser on Wi-Fi
  • SetupAn evening
  • Who seesWhole team, all machines

You see which file his agent is editing, what it ran, what came back, and the PostToolUseFailure and permission events, which is where "stuck on my design system" shows up. Payloads carry the tool input, so you can filter for edits under his design-system folder. Your sessions land on the same board.

Limits. Reference dashboards are demo-grade: no login, SQLite, one process. Fine on a trusted LAN. Hooks carry actions, not the model's reasoning text. Pair with 01 or 02 for the why.
Candidates and config
  • disler/claude-code-hooks-multi-agent-observability (~1.5k stars): swim lane per session, live chart, filters. Bun server on :4000, Vue client on :5173. Hooks are scripts that POST to /events, so the endpoint can be another machine.
  • simple10/agents-observe (~650 stars, maintained): installs as a Claude Code plugin, shows tool calls, file ops, subagent tree, replay, on :4981. Built for one machine; a shared box needs a small patch.
{
  "hooks": {
    "PostToolUse": [{ "matcher": "Edit|Write|Bash",
      "hooks": [{ "type": "http", "url": "http://lan-box:4000/events" }] }],
    "PostToolUseFailure": [{ "hooks": [{ "type": "http", "url": "http://lan-box:4000/events" }] }],
    "Stop": [{ "hooks": [{ "type": "http", "url": "http://lan-box:4000/events" }] }]
  }
}

Hooks can also block. Later, a hook can run your design-system check after every edit and refuse the turn when a raw hex colour appears.

04

OpenTelemetry to a collector, Grafana on top

Claude Code has built-in OpenTelemetry export. Six environment variables turn it on. It emits cost, tokens, lines changed, and an event per prompt, tool result and API call. Content is redacted by default; OTEL_LOG_TOOL_DETAILS and OTEL_LOG_ASSISTANT_RESPONSES add what the agent said and did.

  • Live5 s batches
  • PhoneGrafana, cramped
  • SetupA day, then free
  • Who seesWhole org, by policy

This is the fleet view. An admin pushes the settings to everyone through managed settings, so every agent in the company reports to one collector without opt-in. Grafana has a Claude Code integration and community dashboards. Good at "how much, who, at what cost". Worse than 03 at "what went wrong with Button".

Limits. Someone runs a collector plus a store. Content flags put prompts and responses in that store, so agree on retention. Traces are beta.
Switch-on 
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://lan-box:4318
OTEL_LOG_TOOL_DETAILS=1
OTEL_RESOURCE_ATTRIBUTES=team=console,person=him

Events to chart: claude_code.tool_result with success, tool_name, error_type; claude_code.user_prompt to line failures up with what was asked. Bridges exist that turn hook events into OTel spans, so 03's detail can land in 04's dashboards.

05

GitLab runs the agent. You press the button.

GitLab maintains a beta integration that runs Claude Code in a CI job: one job in .gitlab-ci.yml, one masked API key. You trigger it from "Run pipeline" on your phone, type the task as a pipeline variable, get a merge request back with a diff. Self-managed GitLab works.

  • LiveJob log
  • PhoneGitLab web UI
  • SetupHalf a day + runner
  • Who seesAnyone in the project

The point is not the log. It is that you can re-run the restyle yourself after changing the design system, without his laptop. Both of you get the same environment. If the company has GitLab Premium or Ultimate with Duo, the Agent Platform's Sessions page shows each run step by step with approve and reject checkpoints. That is the most phone-native version of all this.

Limits. Beta. Fresh session per run, no memory. @claude mention triggers need a small webhook listener you host; a community project ships one. Runner minutes and API tokens cost money.
The job, trimmed 
claude:
  stage: ai
  image: node:24-alpine3.21
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  before_script:
    - apk add --no-cache git curl bash
    - curl -fsSL https://claude.ai/install.sh | bash
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    - claude -p "${AI_FLOW_INPUT:-Apply the design system to the console}"
        --permission-mode acceptEdits
        --allowedTools "Bash Read Edit Write mcp__gitlab"
06

A chat channel for pings and questions

Channels (research preview) let a Telegram or Discord bot push messages into a running session and Claude reply in the same chat. He allowlists your sender ID; you ask his agent "what did the Button migration do?" from your phone. Cheaper and not preview: a Stop or Notification hook that posts to a Discord or Slack webhook, so you know when a run finished or is waiting on permission.

  • LivePush
  • PhoneIt's a chat
  • SetupAn hour
  • Who seesAllowlisted senders
Limits. Preview; syntax may change. Team and Enterprise orgs need an Owner to enable channels. Anyone on the allowlist can approve tool permissions if the channel relays them. Not on Bedrock or gateway setups.
07

His terminal in your phone's browser

The screen-share idea, done with one binary. ttyd serves any terminal as a web page, read-only by default, with a password, over the LAN. Warp does the same for its own agent sessions with a nicer viewer, but only for Warp's agent.

  • LiveYes
  • PhoneWraps badly
  • Setup10 minutes
  • Who seesAnyone with the URL
Limits. Synchronous. Nothing recorded. No search, no filter. One afternoon of pairing, not weeks of iteration.
Commands 
tmux new -s restyle        # then run: claude
ttyd -i 0.0.0.0 -c you:pass tmux attach -t restyle
# you open http://his-ip:7681

The mailbox that works: a GitLab issue with a fixed shape

Same place, same template, both agents. His agent files an issue labelled ds-feedback in the design-system project whenever the system blocks it: a missing token, a missing component state, two rules that contradict. Your agent reads open issues at session start, proposes the change, closes the issue with the fixing version. You triage from your phone in between. The rule lives in his CLAUDE.md, so it applies every session. The agent posts via the GitLab MCP server or glab.

## DS feedback (filed by the agent, keep the headings)
Component: Button
Where: src/console/panels/ArmToggle.tsx:42
Needed: a "danger" variant with a pressed state
Tried: primary + custom bg — rejected by ds:check (raw hex)
Design-system version: 0.4.2
Blocking: yes

Add Entire and the loop closes: the issue links the commit, the commit links the checkpoint, and your agent can read exactly what his tried before it gave up.

Replace the zip

A zip has no version, no rules the agent loads by itself, and no way to tell whether it applied them. This layout in a repo on your GitLab fixes each. Editing a file in GitLab's web editor and pressing Commit works from a phone.

design-system/ ├── DESIGN.md colours, type, spacing, do's and don'ts, prose + YAML ├── tokens.json same values as W3C DTCG design tokens, greppable JSON ├── CLAUDE.md rules his agent loads every session; imports DESIGN.md ├── src/ the real components, as now ├── stories/ Storybook, optional; gives the agent a docs API ├── scripts/ds-check stylelint rule: no raw colours or spacing, tokens only ├── .claude/ │ ├── skills/apply-design-system/SKILL.md the how-to │ └── settings.json hooks: run ds-check after edits, post events to the LAN box ├── .gitlab/issue_templates/ds-feedback.md the mailbox shape └── CHANGELOG.md what changed per version; agents read this first

Why each line. DESIGN.md is Google's format from March 2026; Claude Code, Cursor and Gemini read it, and its linter checks token references and contrast and prints JSON. tokens.json in DTCG, stable since October 2025, is the one format every tool in the chain agrees on. CLAUDE.md is the only file Claude Code loads unasked, so the rule "components from this package, never raw hex, file ds-feedback when blocked" goes there. The check script turns "did it get it right" into a command the agent runs itself, and a hook can run it after every edit.

How it reaches him. He clones the repo and adds it with --add-dir; or CI publishes the components as an npm package to the GitLab package registry and his app pins a version; or the .claude folder becomes a Claude Code plugin and the repo a private marketplace, installed with one command. The plugin route ships the hooks and the skill too, so you configure his monitoring, not him.

Your visual-cook skill already has this shape: a single SKILL.md a session auto-discovers. The design system wants the same, plus tokens and a check.

Rollout to the company

The order of ease: things nobody has to do, then things one admin does once, then things each person does once. Keep the pilot inside the first ring. Only grow into the others when the pilot has shown the value.

Ring 0 · in the repo. Nobody installs anything.

Files committed to the console repo apply to everyone who opens it, whichever agent they use. This is the whole pilot. He clones, he works, you watch.

console-app/ ├── AGENTS.md the rules; Cursor, Codex and Gemini read this name ├── CLAUDE.md one line: @AGENTS.md (Claude Code reads this name) ├── DESIGN.md · tokens.json · scripts/ds-check from the design-system repo, or a package pin ├── .claude/ │ ├── skills/apply-design-system/SKILL.md Agent Skills standard, 40+ tools read it │ └── settings.json hooks: POST tool events to the LAN box; run ds-check after edits ├── .agents/skills → ../.claude/skills symlink; Codex and others look here ├── .cursor/hooks.json same events for Cursor users, via the opentelemetry-hooks bridge └── .gitlab/issue_templates/ds-feedback.md the mailbox shape
  • Project hooks run for every teammate. Hooks in .claude/settings.json are shareable by design; they start after the person accepts the workspace-trust dialog on first open. No per-machine config. Works on Linux, Mac, Windows the same way, because an HTTP hook is just a POST.
  • One rules file, two names. Cursor, Codex and Gemini CLI read AGENTS.md. Claude Code reads CLAUDE.md, which imports it. Nobody maintains two copies.
  • One skill, every agent. The SKILL.md format is now an open standard adopted by Cursor, Codex, Gemini CLI and Claude Code. Keep it in .claude/skills, symlink .agents/skills.
  • The LAN box is a URL. Anyone views it in a browser. No client to install, no account.

Ring 1 · the admin console, once. Every Claude Code user, every OS.

Claude Code is org-wide, so the Claude-specific parts go through server-managed settings in the claude.ai admin console (Team and Enterprise). Every machine fetches them at startup and polls hourly. Nothing is copied to laptops. A hook or an env change asks each developer to accept once in an interactive session; after that it just applies.

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://otel.internal:4318",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
    "OTEL_LOG_TOOL_DETAILS": "1"
  },
  "hooks": {
    "PostToolUseFailure": [{ "hooks": [{ "type": "http", "url": "http://agents.internal/events" }] }],
    "Stop":               [{ "hooks": [{ "type": "http", "url": "http://agents.internal/events" }] }]
  },
  "extraKnownMarketplaces": {
    "company": { "source": { "source": "git", "url": "https://gitlab.internal/design/claude-plugins.git" } }

  "enabledPlugins": { "design-system@company": true }
}
  • Marketplace on your GitLab plus enabledPlugins means the design-system plugin (skill, hooks, check) arrives on every machine without anyone running an install command. Bump the version in the marketplace, everyone gets it.
  • No admin console access? The same JSON as a file: /etc/claude-code/managed-settings.json on Linux and WSL, /Library/Application Support/ClaudeCode/ on macOS, C:\Program Files\ClaudeCode\ on Windows. Whatever already pushes files to laptops can place it.
  • Cursor and Gemini don't read these. Gemini CLI has its own OpenTelemetry export that can point at the same collector. Cursor hooks feed the same dashboard through the opentelemetry-hooks bridge. Codex is the odd one out; Entire covers it.

Ring 2 · per person, one command, opt-in

  • entire enable in a repo. This is the one layer that is the same for Claude Code, Cursor, Codex, Gemini and Copilot CLI users: every agent session gets committed next to the code. Homebrew on Mac and Linux, Scoop on Windows. Worth making it the one thing you ask everyone to do, because it is tool-agnostic and it is what lets people read each other's agent work in the repo they already have.
  • claude --remote-control plus the share toggle, for anyone who wants their session readable on a phone.

The pilot, and what "went nice" means

Two weeks, one teammate, ring 0 only, plus entire enable if he is willing. Decide the pass marks before you start so the rollout decision is not a vibe:

  • You never had to sit at his desk to know what the agent did. You answered it from the dashboard, the share link or the checkpoints.
  • Every time the agent got stuck on the design system, a ds-feedback issue appeared, and you closed each with a version bump he could pull.
  • His MR passes ds-check without hand fixes.
  • He would keep the hooks and the rules file if you took them away tomorrow.

If those hold, rollout is mechanical: the ring-0 files become a template that a script drops into any repo, and the admin flips ring 1 once. If they don't, the fix is in the design system package, not in more monitoring.

Vocabulary

Hook
A script or URL Claude Code calls at a named moment, like after a tool runs. Gets the event as JSON. Can log it or block the action.
OpenTelemetry (OTel)
Standard for shipping metrics, logs and traces to a monitoring backend. A collector receives; Grafana draws.
Remote Control
Claude Code's mirror of a local session to claude.ai and the phone app. Execution stays on the laptop; the account that started it owns it.
Checkpoint (Entire)
An agent session stored in git refs next to the commit it produced. Readable by anyone who can pull.
Cross-session messaging
One Claude session sending text to another session of the same person. Same machine uses a socket; other machines go through Anthropic.
MCP server
A small program that gives an agent tools or documents on request. Storybook, Figma and GitLab all offer one.
Managed settings
Settings an admin pushes to every Claude Code install, from the claude.ai console or a file on each machine. Can set env, hooks, marketplaces, permissions. Users cannot override them.
AGENTS.md
The rules-file name Cursor, Codex and Gemini read. Claude Code reads CLAUDE.md, which can import it.
Skill, plugin
A skill is a Markdown how-to the agent loads when relevant. A plugin bundles skills, hooks and MCP servers so one install configures everything.
Merge request (MR)
GitLab's pull request: a proposed change with a diff, line comments, CI results.
Design tokens (DTCG)
Colours, sizes, type as named values in a W3C community group JSON format. Style Dictionary and Tokens Studio read and write it.
DESIGN.md
Markdown plus YAML front matter describing a design system for agents, with a linter and exporters to Tailwind, CSS and tokens.
