Briefing · 2 September 2026 · Claude Code + self-hosted GitLab

Two Agents, One Design System

You ship a design system as a zip. Your co-worker's agent applies it to his machine console. How do you see what his agent does, from your phone, and how do the two agents stop misunderstanding each other?

The short answer

  • Nothing lets you watch another person's Claude Code session live under your own login. That feature is an open request. What exists instead: he shares a read-only session link, or every tool call his agent makes is posted to a small dashboard on the office network, or GitLab becomes the shared record. All three are below, cheapest first.
  • Your agents cannot message each other directly. Claude Code sessions message across machines only when both belong to the same account. Between two people, the mailbox is a GitLab issue with a fixed template that both agents read and write.
  • The zip is the real problem. An agent needs tokens as JSON, rules as Markdown it loads automatically, and a check it can run to know it got things right. A repo on your GitLab with those four files does more for the misunderstanding than any monitoring.

Where each signal actually travels

His agent runs on his laptop and never leaves it. Everything you can see is a copy of something that laptop sends somewhere. There are three destinations, and each one gives you a different kind of view.

Six ways to watch

Rated on the four things you asked about: is it live, does it work on a phone, how much setup, and who else could use it. The first two are things he can do today. The middle two are the real "see each other's agents" answers. The last two turn GitLab into the shared surface.

01

The chair, or a terminal in your phone's browser

Your baseline idea is not weird, it is just low-bandwidth. The technical version of "sit next to him" is a read-only view of his terminal served over the Wi-Fi. A one-binary tool called ttyd serves any terminal as a web page, read-only by default, with a password.

  • LiveYes
  • PhoneCramped
  • Setup10 minutes
  • Who seesAnyone with the URL

You see exactly what he sees, scrolling by. You cannot search it, filter it, or come back to it later, and a wide Claude transcript wraps badly on a phone. Good for one afternoon of pairing, not for the weeks of iteration you described.

Limits. Synchronous only. Nothing is recorded. Both of you must be on the same network at the same moment.
How he sets it up
  1. Run Claude Code inside tmux so the terminal has a name.
  2. Serve it read-only on his LAN address with basic auth.
  3. You open http://his-ip:7681 on your phone.
tmux new -s restyle        # then run: claude
ttyd -i 0.0.0.0 -c you:pass tmux attach -t restyle

VS Code Live Share does the same through Microsoft's relay with a nicer viewer, but VS Code in a phone browser is impractical.

02

He mirrors his session and shares the link

Remote Control mirrors a local Claude Code session to claude.ai/code and the Claude phone app, including a diff pane of his uncommitted changes. Sessions there have a visibility toggle. On a Team or Enterprise plan it is Private or Team. On Pro or Max it is Private or Public. Recipients see the latest state when they open the link, but the view does not update in real time.

  • LiveOn refresh
  • PhoneDesigned for it
  • Setup1 command
  • Who seesYour org, or anyone

You see the whole conversation the way Claude saw it: his prompts, the agent's reasoning, the tool calls, the diff. That is the richest single view of "what issues it is facing", and it needs zero engineering. The catch is that it lives in his account, so he owns the toggle and you only ever look.

Limits. Needs a claude.ai login on his side, not an API key, a Bedrock setup or a company LLM gateway. On Team plans an Owner has to switch Remote Control on in the admin settings. The sharing toggle is documented for cloud sessions; Remote Control sessions appear in the same list, but confirm the toggle shows for his session before you plan around it, a five-minute test. True multi-user viewing is an open request (issues 40981 and 60082 on the Claude Code repo).
How he does it, and the fallback
  1. In his project: claude --remote-control "console restyle", or /remote-control inside a running session.
  2. Open the session at claude.ai/code, set visibility to Team, send you the link.
  3. When a run ends, /export restyle-1.md writes the whole conversation to a file he can drop in the design-system repo. That is your after-the-fact record if the link is not enough.

A neat trick for your own agent: claude -p --resume <session-id> "list every place the design system was unclear" asks a finished transcript a question and prints the answer. It only works on the machine that holds the transcript, so it is something he runs and pastes.

03 Recommended for "see each other's agents"

Every tool call posts to a dashboard on the LAN

Claude Code fires a hook at about thirty moments in a session: before and after every tool call, when a tool fails, when it needs permission, when it stops. A hook can be an HTTP POST of the event's JSON to any URL. Point it at a small server on a spare machine in the office and you have a live, searchable timeline of every agent in the room, per person and per session. Two open-source dashboards already do exactly this.

  • LiveUnder a second
  • PhoneAny browser on Wi-Fi
  • SetupAn evening
  • Who seesWhole team, all machines

You see, for his session: which file it is editing, what command it ran, what came back, and above all the PostToolUseFailure and permission events, which is where "the agent is stuck on my design system" actually shows up. Because the payload carries the tool input, you can filter for edits to files under his design-system folder and ignore the rest. Your own sessions land on the same board, so he can watch you too.

Limits. The reference dashboards are demo-grade: no login, SQLite, one Bun process. Fine on a trusted office LAN, not for exposing beyond it. Hooks do not carry the model's reasoning text, only the actions; pair with option 02 or an export for the "why".
What it looks like in practice

Two candidates, both consuming the same hook feed:

  • claude-code-hooks-multi-agent-observability (disler, ~1.5k stars). Swim lane per session, live pulse chart, event filters, chat transcripts. A Bun server on port 4000 and a Vue client on 5173. Hooks are shell scripts that POST to /events, so the endpoint can be another machine.
  • agents-observe (simple10, ~650 stars, actively maintained). Installs as a Claude Code plugin, shows tool calls, file operations, subagent tree, token stats and session replay on port 4981. Built for one machine; pointing it at a shared box needs a small patch.

The hook config that makes any of this work sits in his .claude/settings.json. The Notification and Stop events are the ones worth turning into a phone ping.

{
  "hooks": {
    "PostToolUse": [{ "matcher": "Edit|Write|Bash",
      "hooks": [{ "type": "http",
                  "url": "http://lan-box:4000/events" }] }],
    "PostToolUseFailure": [{ "hooks": [{ "type": "http",
                  "url": "http://lan-box:4000/events" }] }],
    "Stop": [{ "hooks": [{ "type": "http",
                  "url": "http://lan-box:4000/events" }] }]
  }
}

Because a hook can also refuse an action, the same mechanism can later enforce the design system: a hook that runs your check script after every edit and blocks the turn with a reason when a raw hex colour sneaks in.

04

OpenTelemetry to a collector, dashboards in Grafana

Claude Code has built-in OpenTelemetry export, the industry-standard way to ship metrics and logs to a monitoring stack. Six environment variables turn it on. It emits cost, tokens, lines changed, and an event per prompt, per tool result and per API call. By default the content is redacted; flags like OTEL_LOG_TOOL_DETAILS and OTEL_LOG_ASSISTANT_RESPONSES add what the agent said and did.

  • Live5 s batches
  • PhoneGrafana, cramped
  • SetupA day, then free
  • Who seesWhole org, by policy

This is the fleet view. An admin can push the settings to every developer through managed settings, so all agents in the company report to one collector without anyone opting in. Grafana already has a Claude Code integration and community dashboards. It answers "how much, how often, who, at what cost" very well and "what exactly went wrong with my Button component" less well than option 03.

Limits. Someone has to run a collector plus a store (Prometheus and Loki, or ClickHouse). The content flags mean prompts and responses sit in that store, so agree on retention. Traces are still beta.
The switch-on 
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://lan-box:4318
OTEL_LOG_TOOL_DETAILS=1
OTEL_RESOURCE_ATTRIBUTES=team=console,person=him

The events you would chart: claude_code.tool_result with success, tool_name and error_type, and claude_code.user_prompt to line the failures up against what was asked. Options 03 and 04 are not either-or; there are bridges that turn hook events into OpenTelemetry spans so the detail of 03 lands in the dashboards of 04.

05

GitLab runs the agent, and you press the button

This changes who owns the environment. GitLab maintains a beta integration that runs Claude Code inside a CI job: one job in .gitlab-ci.yml and one masked API key. You trigger it from the "Run pipeline" button on your phone, type the task as a pipeline variable, and the result arrives as a merge request with a diff you can comment on. Self-managed GitLab is supported.

  • LiveJob log
  • PhoneGitLab web UI
  • SetupHalf a day + runner
  • Who seesAnyone in the project

You see the job log while it runs and the MR when it finishes. More importantly, you can re-run the restyle yourself after changing the design system, without touching his laptop and without waiting for him. That is the "I have no control over his environment" problem solved by giving both of you the same environment. If your company has GitLab Premium or Ultimate with Duo, the Agent Platform's Sessions page shows each agent run step by step with approve and reject checkpoints, which is the most phone-native version of all of this.

Limits. Beta, maintained by GitLab rather than Anthropic. Each run is a fresh session with no memory. Mention triggers on @claude need a small webhook listener you host yourself; a community project ships one. Pipelines cost runner minutes and API tokens.
The job, trimmed 
claude:
  stage: ai
  image: node:24-alpine3.21
  rules:
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  before_script:
    - apk add --no-cache git curl bash
    - curl -fsSL https://claude.ai/install.sh | bash
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    - claude -p "${AI_FLOW_INPUT:-Apply the design system to the console}"
        --permission-mode acceptEdits
        --allowedTools "Bash Read Edit Write mcp__gitlab"

The prompt can be short because the rules live in the repo's CLAUDE.md, which the job reads like any session would.

06

A chat channel for pings and questions

Channels are a research-preview feature where a Telegram or Discord bot pushes messages into a running session and Claude replies in the same chat. He allowlists your sender ID, and you can ask his agent "what did the Button migration do?" from your phone and get an answer. A cheaper version, with no preview flags, is a Stop or Notification hook that posts to a Discord or Slack webhook so you know when a run finished or is waiting for permission.

  • LivePush
  • PhoneIt is a chat
  • SetupAn hour
  • Who seesAllowlisted senders
Limits. Research preview; syntax may change. Team and Enterprise organisations must have an Owner enable channels. Anyone on the allowlist can also approve tool permissions if the channel relays them, so treat it as handing over a key. Not available on Bedrock or gateway setups.

Can the agents talk to each other?

Only in the narrow cases Claude Code supports today. The table is the honest map; the pattern below it is what works between two people.

BetweenWorks?How
Two of his sessions, same laptopYesOver a local socket, no servers. Claude uses ListAgents and SendMessage on its own.
His session and his cloud session, or his other machineYesThrough Anthropic servers, only while Remote Control is on, only within his account.
Subagents or an agent team inside one sessionYesBuilt in; agent teams are experimental and single-machine.
His session and your sessionNoNo cross-account messaging exists. A2A, the industry agent-to-agent protocol, hit 1.0 this year but Claude Code does not speak it.

The mailbox that does work: a GitLab issue with a fixed shape

Give both agents the same place to write and the same template to write in. His agent files an issue labelled ds-feedback in the design-system project whenever the system blocks it: a token that does not exist, a component state that is missing, a rule that contradicts another. Your agent reads open issues when you start a session, proposes the change, and closes the issue with the version that fixes it. You triage from your phone in between. The instruction lives in his repo's CLAUDE.md, so it is enforced every session, and the agent can use the GitLab MCP server or the glab command to post.

## DS feedback (filed by the agent, do not edit the headings)
Component: Button
Where: src/console/panels/ArmToggle.tsx:42
Needed: a "danger" variant with a pressed state
Tried: primary + custom bg — rejected by ds:check (raw hex)
Design-system version: 0.4.2
Blocking: yes

This is the same shape a human bug report has, which is the point: the misunderstanding you sense between the two of you is mostly that neither agent knows what the other one was missing. A form fixes that better than a protocol.

Replace the zip

A zip is a pile of files with no version, no rules the agent loads automatically, and no way to tell whether it applied them. A repository on your GitLab with the following layout fixes each of those. Nothing here needs git skill beyond editing a file in GitLab's web editor and pressing Commit, which works from a phone.

design-system/ ├── DESIGN.md colours, type, spacing, do's and don'ts, in prose + YAML ├── tokens.json the same values as W3C DTCG design tokens, greppable JSON ├── CLAUDE.md rules his agent loads every session; imports DESIGN.md ├── src/ the real components, as now ├── stories/ Storybook, optional, gives the agent a docs API ├── scripts/ds-check stylelint rule: no raw colours or spacing, tokens only ├── .claude/ │ ├── skills/apply-design-system/SKILL.md the how-to, step by step │ └── settings.json hooks: run ds-check after edits, post events to the LAN box ├── .gitlab/issue_templates/ds-feedback.md the mailbox shape └── CHANGELOG.md what changed per version, agents read this first

Why each line helps an agent. DESIGN.md is a Google-backed format from March 2026 that Claude Code, Cursor and Gemini all read; its linter validates token references and contrast and prints JSON. tokens.json in the W3C DTCG format, stable since October 2025, is the one thing every tool in the chain agrees on. CLAUDE.md is the only file Claude Code loads without being asked, so the two-line rule "use components from this package, never raw hex, file a ds-feedback issue when blocked" belongs there. The check script is what turns "did it get it right" from your eyeballs into a command the agent runs itself, and a hook can run it after every edit.

How it reaches him. Three routes, pick by how much CI you want: he clones the repo and adds it with --add-dir; or CI publishes the components as an npm package to the GitLab package registry so his app pins a version; or you turn the .claude folder into a Claude Code plugin and the repo into a private plugin marketplace, which his session installs with one command. The plugin route also ships the hooks and the skill, so his monitoring is configured by you, not by him.

Your own visual-cook skill is a good model here: it already ships as a single SKILL.md that a session auto-discovers. The design system wants the same shape, plus tokens and a check.

  • At the end of each run he types /export and drops the file in a shared folder. That is your archive.
  • You add the ds-feedback issue template to the GitLab project and the two-line rule to his CLAUDE.md. From now on the agent tells you what it was missing.

  • Stand up the hook dashboard (option 03) on any spare machine. Both of you point your hooks at it. This is the "see each other's agents" you asked for, and it covers your sessions too.

Vocabulary

The terms the options above lean on, in one line each.

Hook
A script or URL Claude Code calls at a named moment, such as after a tool runs. It gets the event as JSON and can log it, or block the action with a reason.
OpenTelemetry (OTel)
A vendor-neutral standard for sending metrics, logs and traces from software to a monitoring backend. A collector receives them; Grafana draws them.
Remote Control
Claude Code's mirror of a local session to claude.ai and the phone app. Execution stays on the laptop; the account that started it owns it.
Cross-session messaging
One Claude session sending plain text to another of the same person's sessions. Same machine uses a local socket; other machines go through Anthropic.
MCP server
A small program that gives an agent tools or documents on request, like "list the components" or "run this story's tests". Storybook, Figma and GitLab all offer one.
Skill and plugin
A skill is a Markdown how-to the agent loads when relevant. A plugin bundles skills, hooks and MCP servers so one install configures everything.
Merge request (MR)
GitLab's name for a pull request: a proposed change with a diff people can comment on line by line, and CI results attached.
Design tokens (DTCG)
Your colours, sizes and type as named values in a JSON format standardised by the W3C community group. Style Dictionary and Tokens Studio read and write it.
DESIGN.md
A Markdown file with YAML front matter that describes a design system for agents, with a linter and exporters to Tailwind, CSS and tokens.
